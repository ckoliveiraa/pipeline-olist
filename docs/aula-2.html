00 · Correção ao vivo

O que o dado é capaz de responder

Os dez indicadores de cada um, na tela — já consolidados em Indicadores da turma. A correção não é para dar nota — é para separar, em voz alta, três pilhas:

DáToda coluna necessária existe, e o caminho entre as tabelas também.Ticket médio, vendas por mês, nota média por categoria
Dá, mas…As colunas existem, mas ainda são texto ou têm nulo que muda a resposta. É a pilha que vira a aula de hoje.Prazo de entrega: a data é VARCHAR, e 2.965 pedidos não têm data de entrega

A pergunta que ficou no anexo

No fim do guia da aula 1 ficou uma provocação: clientes e pedidos têm exatamente 99.441 linhas cada. Coincidência? Não. Rode no notebook:

SELECT count(*)                            AS linhas,
       count(DISTINCT customer_id)         AS customer_id,
       count(DISTINCT customer_unique_id)  AS customer_unique_id
FROM raw.clientes;
linhas  customer_id  customer_unique_id
99.441       99.441              96.096

A Olist gera um customer_id novo a cada pedido. A pessoa de verdade é o customer_unique_id: 96.096 clientes fizeram 99.441 pedidos. Quem escreveu "clientes que voltaram a comprar" usando customer_id chegaria a zero recompra — sem erro nenhum na tela. Guarde o caso: é o primeiro exemplo do curso de uma coluna cujo nome mente sobre o que ela é.

Como as nove tabelas se ligam

A dúvida mais comum nas entregas foi "como eu ligo uma tabela na outra?". Este é o mapa. Guarde: ele volta na aula 3, em todo JOIN.

PK (chave primária) é a coluna que identifica uma linha da tabela, sem repetir. FK (chave estrangeira) é a coluna que aponta para a PK de outra tabela — é por ela que o JOIN passa. 1 : N se lê na ordem do desenho: um pedido, vários itens. A geolocalização está tracejada de propósito: como ela se liga é parte do desafio 2.

LigaçãoPela colunaTipoO que o dado mostra
clientes ↔ pedidoscustomer_id1 : 1Cada pedido tem o seu próprio customer_id. A pessoa é o customer_unique_id.
pedidos → itens_pedidoorder_id1 : N9.803 pedidos têm mais de um item (até 21). 775 não têm nenhum.
pedidos → pagamentosorder_id1 : NAté 29 pagamentos num pedido só. 1 pedido não tem pagamento.
pedidos → avaliacoesorder_id1 : N768 pedidos sem avaliação; até 3 num pedido.
itens_pedido → produtosproduct_idN : 1Todo item encontra o seu produto.
itens_pedido → vendedoresseller_idN : 1O vendedor é do item, não do pedido: 1.278 pedidos têm mais de um vendedor.
produtos → traducao_categoriasproduct_category_nameN : 12 categorias não têm tradução.

Como usar o mapa: para juntar duas tabelas que não se tocam, siga as linhas entre elas. Cada linha que você atravessa é um JOIN ... ON, com a coluna escrita na linha. O valor do item está em itens_pedido e o estado está em clientes; o caminho entre os dois passa por pedidos:

SELECT c.customer_state, count(*) AS itens_vendidos
FROM raw.itens_pedido AS i
JOIN raw.pedidos      AS p ON p.order_id    = i.order_id      -- linha order_id
JOIN raw.clientes     AS c ON c.customer_id = p.customer_id   -- linha customer_id
GROUP BY c.customer_state
ORDER BY itens_vendidos DESC;

Repare no lado N das ligações: juntar pedidos com itens_pedido transforma 99.441 linhas em 112.650, porque cada pedido aparece uma vez por item. Contar pedidos depois desse JOIN exige count(DISTINCT order_id) — senão o pedido de três itens conta três vezes.

Os indicadores escolhidos hoje viram os marts da aula 3. Anote no seu indicadores.md quais foram, e em que pilha cada um caiu. Os da pilha do meio são exatamente o que a transformação precisa destravar.

02 · Fundamento

Tipos de dados em cinco minutos

Na aula 1, tudo entrou em raw como VARCHAR — texto —, de propósito. Boa parte do trabalho de hoje é dar a cada coluna o tipo do que ela realmente é. E o tipo de uma coluna decide duas coisas: o que cabe nela e o que dá para fazer com ela.

TipoGuardaNa OlistCuidado
VARCHARTexto, de qualquer tamanhoorder_id, customer_state, CEPCompara e ordena letra a letra, não por valor
INTEGERNúmero inteiropayment_installments, product_weight_gPara contagem e medida; BIGINT quando passa de 2 bilhões
DECIMAL(p,s)Número com casas decimais exatasprice, payment_valueDECIMAL(10,2): até 10 dígitos, 2 depois da vírgula. É o tipo do dinheiro
DOUBLENúmero com vírgula, aproximadomédias, porcentagensRápido, mas erra na última casa. Nunca para dinheiro
BOOLEANtrue ou falsenenhuma coluna aindaVocê vai criar um na aula 3: entregue no prazo, sim ou não
DATEUm dia, sem horaorder_estimated_delivery_dateSubtrair duas datas dá o número de dias entre elas
TIMESTAMPDia e horaorder_purchase_timestampAceita date_trunc, extract, comparação no tempo

E o NULL? Não é um tipo: é a ausência de valor, e pode aparecer em uma coluna de qualquer tipo. Uma coluna TIMESTAMP com nulo continua sendo TIMESTAMP — só tem linhas em que a data não existe.

Cinco consultas para ver a diferença

Nenhuma delas precisa das tabelas. Suba o notebook do DuckDB (uv run python ui.py) — ele fica aberto também para a investigação — e rode cada uma numa célula. Antes de rodar, chute o resultado.

1 · texto não é número

SELECT max(x) AS maior FROM (VALUES ('9'), ('10'), ('100')) AS t(x);

Resposta: '9'. Em texto, '9' vem depois de '1', como "zebra" vem depois de "abacaxi". Nenhum erro, nenhum aviso. Uma entrega do desafio 1 rodou max(price) em raw.itens_pedido e encontrou R$ 999,99 como o maior preço da Olist. O maior de verdade é R$ 6.735,00.

2 · dinheiro não é DOUBLE

SELECT 0.1::DOUBLE + 0.2::DOUBLE              AS double,
       0.1::DECIMAL(10,2) + 0.2::DECIMAL(10,2) AS decimal;

0.30000000000000004 contra 0.30. O DOUBLE guarda uma aproximação binária do número; em uma soma isso some, em cem mil somas vira centavo que não fecha. O :: é o jeito curto de converter: valor::TIPO é o mesmo que CAST(valor AS TIPO).

3 · data em texto não faz conta

SELECT DATE '2018-03-01' - DATE '2018-02-01' AS dias;

28. Agora tire o DATE das duas e rode de novo: Binder Error. É por isso que nenhum indicador de prazo de entrega sai de raw.

4 · nem tudo que parece número é número

SELECT '01151'::INTEGER AS cep;

1151. O zero da frente sumiu, e com ele o CEP. CEP, order_id e telefone têm cara de número, mas são identificadores: ninguém soma CEP. Ficam VARCHAR.

5 · nulo não é igual a nada, nem a outro nulo

SELECT NULL = NULL AS igual, NULL IS NULL AS e_nulo;

NULL e true. Comparar com nulo dá nulo, porque "não sei" comparado com "não sei" continua "não sei". Para achar nulos, só IS NULL funciona; um WHERE coluna = NULL devolve zero linhas, sem erro.

A regra de bolso

  1. Vai fazer conta com isso? Se não, é VARCHAR, por mais que pareça número.
  2. É dinheiro? DECIMAL.
  3. Conta coisas inteiras? INTEGER.
  4. É um momento no tempo? TIMESTAMP se a hora importa, DATE se não.

No pandas os nomes mudam — object, int64, float64, datetime64, bool — e falta um: o pandas não tem DECIMAL nativo, e dinheiro vira float64 sem avisar. Guarde isso para quando for decidir onde a conversão acontece.

Na investigação a seguir, a pergunta por trás de cada célula é sempre a mesma: que tipo esta coluna deveria ter, e o dado deixa?

03 · Passo a passo

Investigar antes de limpar

A regra da aula, numa frase: você não limpa o que não contou. Antes de decidir o que fazer com um nulo, você precisa saber quantos são, onde estão e o que significam. Quinze minutos de notebook agora economizam a aula inteira de "por que meu número mudou?".

2.1

Seis perguntas ao dado

No notebook do DuckDB, em raw

uv run python ui.py

Uma célula por pergunta. Antes de rodar cada uma, chute o resultado — a diferença entre o chute e a resposta é o que você aprende.

Célula 1 · quantos nulos nas datas de pedido?

SELECT count(*)                                      AS linhas,
       count(*) - count(order_approved_at)           AS sem_aprovacao,
       count(*) - count(order_delivered_carrier_date) AS sem_envio,
       count(*) - count(order_delivered_customer_date) AS sem_entrega
FROM raw.pedidos;

Esperado: 99.441 linhas, 160 sem aprovação, 1.783 sem envio, 2.965 sem entrega. O truque do count(*) - count(coluna): count(coluna) ignora nulos, então a diferença é exatamente quantos são.

Célula 2 · o nulo é erro ou é informação?

SELECT order_status,
       count(*)                                        AS pedidos,
       count(*) - count(order_approved_at)             AS sem_aprovacao,
       count(*) - count(order_delivered_customer_date) AS sem_entrega
FROM raw.pedidos
GROUP BY order_status
ORDER BY pedidos DESC;

Esta é a célula da aula. Dos 2.965 pedidos sem data de entrega, 1.107 estão shipped (a caminho), 619 canceled, 609 unavailable… Eles não chegaram porque não era para ter chegado ainda. O nulo está dizendo a verdade. Apagar essas linhas apagaria todos os cancelamentos do dashboard.

Mas olhe a linha delivered: 8 pedidos entregues sem data de entrega, e 14 entregues sem data de aprovação. Esses, sim, são estranhos. Estranho não quer dizer "apague" — quer dizer "anote e decida".

Célula 3 · existe duplicata?

SELECT count(*) AS linhas, count(DISTINCT order_id) AS pedidos_distintos
FROM raw.pedidos;

Esperado: os dois números iguais. Zero duplicatas também é resultado — e você só pode afirmar isso porque contou. Repita para itens_pedido com a chave composta (order_id, order_item_id): um pedido tem vários itens, então order_id sozinho repete por definição, e isso não é duplicata.

Célula 4 · em que formato a data está?

SELECT order_purchase_timestamp,
       length(order_purchase_timestamp) AS tamanho
FROM raw.pedidos LIMIT 5;

2017-10-02 10:56:33, 19 caracteres, ano-mês-dia. Em todas as 99.441 linhas, sem exceção — confira com um GROUP BY tamanho. Formato uniforme é o que permite declarar o formato em vez de deixar adivinhar.

Célula 5 · o formato declarado converte tudo?

SELECT count(*) FILTER (
         WHERE order_purchase_timestamp IS NOT NULL
           AND try_strptime(order_purchase_timestamp, '%Y-%m-%d %H:%M:%S') IS NULL
       ) AS falhas
FROM raw.pedidos;

Esperado: 0. Agora troque o formato por '%d/%m/%Y %H:%M:%S' e rode de novo: 99.441 falhas. É assim que se testa uma conversão antes de confiar nela — o try_ devolve nulo em vez de estourar, e você conta os nulos que ele criou.

Célula 6 · por que o CEP entrou como texto?

SELECT count(*) AS ceps_com_zero_a_esquerda
FROM raw.clientes
WHERE customer_zip_code_prefix LIKE '0%';

23.995. Quase um quarto dos clientes — Grande São Paulo inteira. Se a aula 1 tivesse deixado o pandas inferir o tipo, 01151 teria virado 1151 sem aviso, e o CEP deixaria de casar com qualquer outra tabela. CEP parece número, mas é identificador: nunca vai ser somado. Fica texto.

Confira

Você consegue dizer, sem olhar, quantos pedidos não têm data de entrega e por quê. Se a resposta é "porque o dado é sujo", volte à célula 2.

Agora desligue o servidor. Ctrl+C no terminal do ui.py antes de seguir. Com ele de pé, nem a IA do próximo passo consegue ler o banco, nem a transformação consegue escrever: o banco aceita um escritor por vez, e quem escreve não divide o arquivo com ninguém.

04 · A IA no banco

MCP: a IA para de adivinhar o seu dado

Até aqui, a IA escrevia código sobre um banco que ela nunca viu. Você colava o DESCRIBE, ela supunha o resto. Quando ela erra o nome de uma coluna ou chuta o formato da data, o motivo é esse: ela está trabalhando às cegas.

O MCP (Model Context Protocol) é a peça que tira a venda. É um protocolo aberto para ligar a IA a ferramentas externas — e a ferramenta de hoje é o seu olist.duckdb. Com ele, a IA roda SQL de verdade no seu banco, lê o resultado e decide com base no dado, não no que ela imagina que o dado seja.

Três coisas que o desenho mostra: a IA nunca toca o arquivo diretamente, quem executa é o servidor; toda consulta passa por você antes de rodar; e o servidor tem uma trava própria — somente leitura — que vale independentemente do que a IA quiser fazer.

As três regras do MCP no curso

  1. Somente leitura, sempre que possível. E a trava é do servidor, não do prompt. Pedir "não altere nada" para a IA é um pedido; rodar o servidor sem --read-write é uma garantia. Se ela tentar um CREATE, quem recusa é o DuckDB.
  2. O que a IA rodou no banco não existe para o pipeline. Uma tabela criada por uma consulta no chat some na próxima vez que alguém rodar o pipeline do zero, e ninguém sabe como recriá-la. Toda transformação termina como código em pipeline/transformacao.py. O banco é laboratório; o arquivo é a fonte da verdade.
  3. Leia a SQL antes de aprovar. O Claude Code pede permissão a cada consulta; o Codex, conforme o modo de aprovação da sessão. Se a consulta rodar sem você ver, peça que a IA mostre a SQL junto com cada resposta. Aprovar sem ler é o mesmo que colar código sem conferir — só que agora o código roda no seu dado na hora.
2.2

Conectar a IA ao banco

Claude Code, Codex ou Copilot: o mesmo servidor

O servidor é o mcp-server-motherduck, mantido pela empresa por trás do DuckDB na nuvem — mas ele funciona com arquivo local, sem conta e sem nuvem. O uvx, que veio junto com o uv, baixa e roda o servidor sem instalar nada no projeto.

Antes de tudo, baixe o servidor uma vez, à mão. Na primeira execução o uvx baixa cerca de 70 pacotes, e isso pode estourar o tempo que a IA espera o servidor subir:

uvx mcp-server-motherduck --help

Agora escolha a sua ferramenta. O servidor é o mesmo nas três; muda só o arquivo onde a configuração mora.

Claude Code · na raiz do projeto

claude mcp add --scope project duckdb -- uvx mcp-server-motherduck --db-path olist.duckdb

O --scope project grava a configuração num arquivo .mcp.json na raiz, que vai para o git junto com o código: quem clonar o projeto ganha a mesma conexão. É isto que ele escreve:

.mcp.json

{
  "mcpServers": {
    "duckdb": {
      "type": "stdio",
      "command": "uvx",
      "args": ["mcp-server-motherduck", "--db-path", "olist.duckdb"],
      "env": {}
    }
  }
}

Repare no que não está ali: --read-write. Sem ele, o servidor abre o arquivo em somente leitura e, a cada consulta, abre e fecha a conexão — o arquivo fica destravado entre uma consulta e outra, e o seu pipeline continua conseguindo escrever.

Uso o Codex (OpenAI)

O Codex lê servidores MCP de um arquivo config.toml, em TOML e com mcp_servers em snake_case — não mcpServers. Crie o arquivo .codex/config.toml na raiz do projeto:

.codex/config.toml

[mcp_servers.duckdb]
command = "uvx"
args = ["mcp-server-motherduck", "--db-path", "olist.duckdb"]
startup_timeout_sec = 60

Duas coisas que pegam quem vem do Claude Code:

  • Configuração de projeto só vale em projeto confiável. Na primeira vez que você abre o codex na pasta, ele pergunta se confia nela. Se você recusou, o arquivo acima é ignorado em silêncio.
  • O startup_timeout_sec não é enfeite. O padrão do Codex é esperar 10 segundos o servidor subir, e o uvx pode levar mais que isso. Com 60, sobra folga.

Se preferir o comando em vez do arquivo, o codex mcp add faz o mesmo — mas grava na configuração global (~/.codex/config.toml), que vale em qualquer pasta. Por isso, ali o caminho do banco tem que ser completo:

codex mcp add duckdb -- uvx mcp-server-motherduck --db-path C:/caminho/do/projeto/olist.duckdb

Para conferir: codex mcp list no terminal, ou /mcp dentro do Codex. A extensão do Codex no VS Code usa a mesma configuração do terminal — configurou uma vez, vale nas duas.

Uso o Copilot no VS Code

O VS Code lê o mesmo servidor de um arquivo .vscode/mcp.json, com uma chave diferente na raiz:

{
  "servers": {
    "duckdb": {
      "type": "stdio",
      "command": "uvx",
      "args": ["mcp-server-motherduck", "--db-path", "${workspaceFolder}/olist.duckdb"]
    }
  }
}

Abra o chat do Copilot no modo Agent e ligue as ferramentas do servidor duckdb no ícone de ferramentas.

O ChatGPT no navegador não alcança um arquivo no seu disco. Para esta parte da aula, use Claude Code, Codex ou Copilot.

Abra a IA na pasta do projeto (claude ou codex). Na primeira vez ela pergunta se você confia no projeto — aceite. Depois, digite /mcp: o servidor duckdb tem que aparecer como conectado.

O primeiro teste

Quais tabelas existem no schema raw do meu banco, e quantas linhas tem raw.pedidos?

Confira

A IA chama list_tables ou execute_query — você vê o nome da ferramenta na tela — e a resposta vem com as nove tabelas e 99.441. Se nenhuma ferramenta aparecer, ela não consultou o banco: está chutando. Pergunte de novo, pedindo que mostre a SQL.

Desligue o ui.py antes. Somente leitura não resolve tudo: se outro processo estiver com o banco aberto para escrita — o ui.py, ou a transformação rodando — o servidor MCP também não consegue abrir o arquivo, e a IA recebe o mesmo Could not set lock on file. Um escritor por vez continua valendo.

E quando liberar a escrita?

Somente leitura · o padrão

--db-path olist.duckdb

A IA investiga, testa conversão, conta, compara. Não consegue estragar nada, e o arquivo fica livre para o pipeline. Cobre tudo o que a aula 2 pede.

Leitura e escrita · a exceção

--db-path olist.duckdb --read-write

A IA cria e apaga tabela. O servidor segura o arquivo aberto enquanto o Claude Code estiver de pé, então o pipeline e o ui.py param de funcionar com erro de lock. Se usar, só num schema de rascunho (lab), nunca em raw ou refined — e feche o Claude Code antes de rodar o pipeline.

O dado vai junto. Tudo o que uma consulta devolve é enviado para o modelo de IA. Com a Olist, que é pública, tanto faz. No trabalho, com dado de cliente de verdade, a primeira pergunta antes de conectar um MCP ao banco é se a política da empresa permite que aquele dado saia de lá.

05 · O método

A spec é sua agora

Na aula 1 a spec veio pronta, para você ver o formato. Hoje você escreve. Não porque ficou mais fácil — porque a transformação é cheia de decisões que só você pode tomar, e qualquer uma delas que ficar de fora a IA vai tomar por você, em silêncio, do jeito dela.

As sete decisões da transformação

  1. Escopo: o que vai para refined. Todas as nove tabelas? Nenhum mart do curso usa a geolocalização — e ela é o desafio de casa. Diga o que entra, o que fica de fora, e por quê.
  2. Nomes de coluna. order_purchase_timestamp ou data_compra? A raw não podia renomear — a refined pode. E product_name_lenght vem com erro de digitação de fábrica. Se for renomear, escreva o mapa inteiro, coluna por coluna: é o vocabulário que você vai digitar de memória nos JOIN da aula 3.
  3. O tipo de cada coluna. Data vira TIMESTAMP com formato declarado. Dinheiro vira DECIMAL ou DOUBLE? (A consulta 2 de tipos de dados responde.) Contagem vira inteiro. E o que parece número mas é identificador — CEP, order_item_id? Decida um por um.
  4. O que acontece quando a conversão falha. Vira nulo e segue, ou para tudo? Converter falha em nulo é a forma mais silenciosa de perder dado que existe: os 2.965 nulos reais se misturam com nulos que você fabricou, e ninguém nunca mais separa os dois.
  5. O que é duplicata, tabela por tabela. Qual é a chave de cada uma? Se a chave repetir com conteúdo idêntico, sai. E se repetir com conteúdo diferente — você escolhe uma linha, ou para e avisa?
  6. O que fazer com cada nulo. Manter, apagar a linha, ou preencher? Preencher com zero, com a média, com "desconhecido"? Cada resposta muda um número do dashboard. A célula 2 já te disse o que os nulos de pedidos significam.

Repare que a reexecução e o tratamento de erro não estão na lista: valem as mesmas regras da aula 1. Recria a tabela, nunca acrescenta. Faltou tabela em raw, para com mensagem clara.

Os critérios de aceite, um por um, no notebook

"Rodou sem erro" não é critério de aceite. Suba o ui.py de novo e confira a spec contra o banco:

O tipo mudou?

DESCRIBE refined.pedidos;

É o momento prometido na aula 1: onde estava VARCHAR, agora TIMESTAMP. Coloque lado a lado com DESCRIBE raw.pedidos.

A conversão fabricou nulo?

SELECT 'raw'     AS camada, count(*) - count(order_delivered_customer_date) AS sem_entrega FROM raw.pedidos
UNION ALL
SELECT 'refined', count(*) - count(data_entrega) FROM refined.pedidos;

Os dois têm que dar 2.965. Se refined der mais, a conversão engoliu valores em silêncio — exatamente o que a decisão 4 proibia.

O dinheiro fechou?

SELECT (SELECT sum(CAST(price AS DECIMAL(10,2))) FROM raw.itens_pedido)  AS raw,
       (SELECT sum(preco)                             FROM refined.itens_pedido) AS refined;

O zero do CEP sobreviveu?

SELECT cep_prefixo FROM refined.clientes WHERE cep_prefixo LIKE '0%' LIMIT 3;

E a prova de que data agora é data

SELECT date_trunc('month', data_compra) AS mes, count(*) AS pedidos
FROM refined.pedidos
GROUP BY mes
ORDER BY mes;

Em raw essa consulta nem roda — date_trunc não aceita texto. Em refined ela devolve os 25 meses de vendas, de setembro de 2016 a outubro de 2018. É o primeiro mart do curso, escrito sem querer: semana que vem ele vira arquivo.

A2 · Anexo

Quando quebrar

IO Error: Could not set lock on file

Tem um ui.py de pé — às vezes num terminal que você nem lembra que abriu. Ctrl+C nele. Ou um Claude Code aberto com o servidor MCP em --read-write: feche-o. Se não achar, feche todos os terminais do VS Code. O banco não está corrompido.

Invalid Input Error: Could not parse string ... according to format specifier

É a decisão 4 funcionando: um valor não bate com o formato que você declarou. Não troque strptime por try_strptime para "resolver" — isso esconde o problema. Leia o valor que aparece na mensagem e descubra por que ele é diferente dos outros.

Catalog Error: Table with name ... does not exist

Ou a ingestão não rodou, ou o nome da tabela em raw é diferente do que a spec da transformação assume. Rode SHOW ALL TABLES; no notebook e compare com o seu mapa da aula 1.

Saíram menos linhas do que entraram

Procure dropna, drop_duplicates e WHERE no código. Depois descubra quais linhas sumiram com um anti-join: SELECT * FROM raw.pedidos r WHERE NOT EXISTS (SELECT 1 FROM refined.pedidos f WHERE f.pedido_id = r.order_id). Olhe as linhas antes de decidir se o sumiço é certo.

A soma do dinheiro não bate por centavos

A coluna virou DOUBLE em algum ponto do caminho — muitas vezes porque o código passou pelo pandas, que converte número para float64. Converta direto para DECIMAL(10,2), a partir do texto.

O /mcp não mostra o servidor duckdb, ou mostra com falha

Três suspeitos, nesta ordem. O uvx não está no PATH: rode uvx --version no mesmo terminal. O banco não existe ainda: em somente leitura o servidor não cria arquivo, então rode a ingestão primeiro. O caminho relativo não resolveu: abra o Claude Code na raiz do projeto, ou troque olist.duckdb no .mcp.json pelo caminho completo do arquivo. No Codex, mais dois: o projeto não foi marcado como confiável (e o .codex/config.toml foi ignorado), ou faltou o startup_timeout_sec = 60 e o servidor não subiu a tempo.

A IA diz que não consegue escrever no banco

Está certo, e é a trava funcionando: o servidor está em somente leitura. Não libere a escrita para resolver — peça o SELECT e coloque a escrita no transformacao.py, que é onde ela tem que morar.

Quebrei tudo e não sei onde

Apague o olist.duckdb e rode as duas etapas em ordem. Um minuto, e você está de volta onde a turma está:

uv run python -m pipeline.ingestao
uv run python -m pipeline.transformacao
