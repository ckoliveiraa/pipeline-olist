00 · O destino

O que vamos construir

O dataset da Olist é público e real: todo pedido feito na plataforma entre 2016 e 2018, com item, pagamento, avaliação, vendedor e cliente. Chega até você como nove arquivos .csv soltos numa pasta — do jeito que dado chega no mundo real, sem ninguém para explicar.

No fim das quatro aulas, esses arquivos viram um dashboard que responde perguntas de negócio. Primeiro a planta da casa — onde cada coisa fica e quem escreve o quê:

Tudo isso roda na sua máquina, sem nuvem: o banco inteiro é o arquivo olist.duckdb e não existe banco de dados para instalar. As duas saídas à direita são servidores locais — ui.py para explorar o dado em SQL pelo navegador, app.py para o dashboard. As setas são código seu, e cada uma pode ser rodada de novo, do zero, quantas vezes precisar.

Lido de cima a baixo, o mesmo caminho com o que cada camada entrega:

raw/ Os 9 CSVs — intocados. A gente nunca escreve aqui.
↓ingestao.py · Python lê o arquivo e grava no banco
raw.* Espelho fiel do CSV, agora consultável com SQL.
↓transformacao.py · Python limpa, deduplica, converte data
refined.* Dado confiável — ainda granular: 1 linha = 1 pedido.
↓sql/marts/*.sql · SQL agrega e responde perguntas
marts.* Pronto para consumo — vendas por mês, entrega no prazo.
↓app.py · Streamlit só faz SELECT
dash O dashboard que você abre no navegador.

Três camadas, três nomes, uma regra que vale para todas: qualquer etapa pode ser rodada de novo do zero sem quebrar. Travou no meio da aula? Roda de novo e segue. Ninguém fica para trás.

01 · Antes de começar

Seis palavras que vão aparecer o tempo todo

Nenhuma delas é difícil, mas todas vão ser ditas como se você já soubesse. Então:

TermoO que quer dizer aqui
ingestãoPegar o dado de onde ele está e colocar onde dá para trabalhar. Sem mudar nada — copiar, não corrigir.
transformaçãoTornar o dado confiável: tipo certo, duplicata fora, nulo decidido. É onde mora o julgamento.
martTabela já agregada, feita para responder uma pergunta específica. "Vendas por mês" é um mart.
granularUma linha por evento (um pedido, um item). O oposto de agregado.
idempotenteRodar uma vez ou dez vezes dá o mesmo resultado. É o que deixa você errar sem medo.
DuckDBUm banco analítico que vive num arquivo só, sem servidor. Fala SQL igual ao BigQuery.
Por que DuckDB e não um banco "de verdade". Porque instalar Postgres com Docker custaria os primeiros 40 minutos da aula 1, e o seu tempo aqui é para SQL e Python — não para porta ocupada e WSL. O SQL que você escrever no DuckDB funciona igualzinho no BigQuery e no Snowflake.

Do arquivo para a tabela

Ler os nove CSVs e gravá-los no banco sem mudar nada. Python aqui é caminho de arquivo, laço e função. O momento que fecha a aula é você rodar SELECT * FROM raw.pedidos LIMIT 5 e ver o arquivo virar tabela.

02transformação

Ler o dado ≠ confiar no dado

Aula mais densa e a mais desconfortável, porque não existe resposta certa única. Data que era texto vira timestamp, duplicata sai, e cada nulo vira uma decisão sua — escrita, justificada. É aqui que a IA entra pela primeira vez, e onde você aprende a não acreditar nela.

03SQL

Cinquenta minutos direto de SQL

Quatro arquivos .sql, quatro perguntas de negócio, um degrau de dificuldade cada: GROUP BY, depois JOIN, depois CASE WHEN com datas, e por fim CTE com window function. Sem Python no caminho.

04dash

Dashboard e a rede de segurança

Streamlit lendo os marts — e é rápido justamente porque o trabalho pesado já está no SQL. Sobra tempo para escrever dois ou três testes ao vivo, ver verde, quebrar um .sql de propósito e ver vermelho.

03 · Passo a passo

Preparar a máquina

Faça isto antes da aula 1. São dez minutos em casa que, multiplicados por uma turma, seriam a aula inteira.

00

Instalar o uv

O gerenciador que resolve Python e bibliotecas de uma vez

O uv instala o Python certo e todas as bibliotecas do projeto com um comando só. Sem venv, sem "na minha máquina funciona". A documentação oficial fica em docs.astral.sh/uv — vale deixar aberta numa aba.

Vamos instalar com o pipx, que coloca cada ferramenta Python no seu próprio ambiente isolado:

# 1. pipx (se você ainda não tem)
python -m pip install --user pipx
python -m pipx ensurepath

# 2. uv
pipx install uv

Confira

Feche e reabra o terminal — o ensurepath só vale na próxima sessão — e rode uv --version. Tem que aparecer um número.

01

Criar o projeto

Pasta vazia → ambiente pronto

Escolha onde o projeto vai morar — Documentos, Desktop, tanto faz, contanto que você saiba voltar lá. Um caminho sem acento e sem espaço evita uma classe inteira de dor de cabeça mais adiante.

# 1. criar a pasta e entrar nela
mkdir olist
cd olist

# 2. iniciar o projeto (cria o pyproject.toml)
uv init --bare

# 3. as bibliotecas do curso
uv add duckdb pandas streamlit
uv add --dev pytest ruff

O uv init cria o pyproject.toml, que é a lista de tudo que o projeto precisa, e o uv add vai preenchendo essa lista. O ambiente (.venv) e o uv.lock nascem no primeiro uv add — e, se você não tiver a versão de Python exigida, o próprio uv baixa. Quem clonar seu projeto depois roda uv sync e recebe exatamente as mesmas versões. Daqui para frente, todo comando começa com uv run.

Por que --bare. Sem ele, o uv init monta um projeto empacotável: cria uma pasta src/ e uma seção [build-system] no pyproject.toml. Aí todo uv run passa a tentar construir o projeto antes de rodar — e como nosso código vai morar em pipeline/, e não em src/, ele falha com um erro de build que não tem nada a ver com o que você escreveu. O --bare cria só o pyproject.toml e mais nada.

Confira

uv run python -c "import duckdb, pandas, streamlit" tem que rodar sem dizer nada. Silêncio é sucesso — em Python, notícia só aparece quando é ruim.

02

Conferir os dados

Nove arquivos, 1.550.922 registros

Os nove arquivos estão prontos no repositório do curso — sem conta, sem cadastro, 42 MB:

github.com/ckoliveiraa/pipeline-olist

Clone dentro da pasta do projeto, de um jeito que os dados caiam direto em raw/:

Windows · Prompt de Comando

git clone https://github.com/ckoliveiraa/pipeline-olist.git dados
move dados\raw raw
rmdir /s /q dados

macOS, Linux ou Git Bash

git clone https://github.com/ckoliveiraa/pipeline-olist.git dados
mv dados/raw .
rm -rf dados
Os comandos do terminal mudam conforme onde você digita. rm, mv e ls são do mundo Unix — no Prompt de Comando do Windows eles não existem, e a resposta é 'rm' não é reconhecido como um comando interno ou externo. Lá os nomes são del, move, rmdir e dir. Nada a ver com Python: é só o terminal. Os comandos uv e git, esses funcionam igual em todo lugar.

Sem git instalado? Baixe o ZIP pelo botão verde Code › Download ZIP e mova a pasta raw/ de dentro dele para o seu projeto, pelo explorador de arquivos mesmo.

Os arquivos terminam em .csv.gz — e está certo assim. São os mesmos CSVs, comprimidos: 42 MB em vez de 121 MB. Não descompacte. O pandas lê .csv.gz exatamente como leria um .csv, sem parâmetro nenhum, e o DuckDB também. É de graça e você nem percebe.

Confira

Você tem que enxergar nove arquivos dentro de raw/, soltos, sem subpasta — o pipeline procura por raw/olist_orders_dataset.csv.gz. A lista completa, com o número de registros de cada um, está no anexo de contagens.

A fonte original é o Kaggle: Brazilian E-Commerce Public Dataset by Olist, sob licença CC BY-NC-SA 4.0.

Nunca edite nada dentro de raw/. É a fonte da verdade. Se você abrir um CSV no Excel e salvar, o Excel reescreve datas e números no formato dele e o pipeline inteiro passa a mentir — silenciosamente, que é o pior jeito.

04 · O método

Spec-driven development

O nome é novo, a ideia é velha: decida antes de digitar, e deixe a decisão escrita. O que mudou foi quem digita. Quando o código saía da sua cabeça direto para o teclado, a decisão podia ficar na cabeça. Agora que boa parte dele sai de um prompt, o que não estiver escrito vai ser inventado por outra pessoa — que não conhece o seu dado e não vai avisar que inventou.

A seta pontilhada é o método inteiro em uma linha: o que a IA teve que adivinhar é a medida exata do que faltava na sua spec.

O nome certo para cada coisa

Três palavras que vivem sendo trocadas uma pela outra, e a troca custa caro:

PalavraRespondeQuando é escrita
ArquiteturaQue peças existem e como se ligam — raw → refined → marts, DuckDB no meio, dashboard na ponta.Uma vez, no começo. Muda pouco.
SpecO que esta peça faz e o que ela tem proibido fazer. É um contrato, não uma explicação.Antes de cada etapa. É o que você vai escrever quatro vezes neste curso.
DocumentaçãoComo usar o que já existe.Depois. Conta o passado.

A confusão mais comum é chamar de spec o que é documentação: um texto que descreve o código que já está lá. Esse texto não decide nada — ele concorda com qualquer coisa que o código faça. Spec é o que foi escrito antes, e é só por isso que ela é capaz de dizer que o código está errado.

Por que isso pesa mais agora

Sem spec

prompt → código → rodou?
  → prompt de novo → código…

Sobra uma única pergunta para avaliar a sugestão: rodou? Em código de dados ela não serve de nada — o erro típico roda liso e devolve número errado. E cada volta do ciclo joga a anterior no lixo, porque não existe nada fora do chat dizendo o que era certo.

Com spec

decisões → spec → código
  → confere contra a spec

A pergunta passa a ser respeitou o que eu decidi? — e essa você responde item por item. O que se acumula é a spec, não o histórico de conversa: quando a etapa 2 mudar de ideia, o código é gerado de novo a partir dela em um minuto.

O ganho não é escrever menos código. É ter um critério de aceite que não dependa de você lembrar o que queria vinte minutos atrás.

Spec não é documento longo. As sete decisões da próxima etapa caberiam num guardanapo, e esse é o tamanho certo. Spec grande ninguém escreve antes — e spec escrita depois não é spec, é documentação.

É isto que você vai praticar quatro vezes, uma por etapa: fechar as decisões, escrever, gerar, conferir. A etapa 1 já vem com a spec pronta e com o prompt que sai dela, para você ver o formato antes de escrever o seu na etapa 2. A outra metade — como conferir o que voltou — tem seção própria em A IA como copiloto.

Etapa 1 — Ingestão

Aula 1 · pipeline/ingestao.py

Antes de escrever a primeira linha

Ingestão parece o pedaço bobo do pipeline — ler arquivo e gravar. É o que engana. Quase todo defeito difícil de achar depois nasce de uma decisão que ninguém tomou aqui, e sim deixou acontecer. Feche estas sete antes de abrir o editor; são dez minutos e valem a aula inteira.

  1. Que tabelas existem e como se chamam. Escreva o mapa arquivo → tabela inteiro antes. olist_order_items_dataset.csv.gz vira raw.itens_pedido ou raw.order_items? Traduzir ou manter o original? Não existe resposta certa — existe resposta escrita, porque daqui a duas aulas você vai escrever esse nome de memória num JOIN.
  2. O que é proibido fazer aqui. Diga na spec, com todas as letras: nenhuma conversão de tipo, nenhuma linha descartada, nenhum nome de coluna alterado. Sem essa frase, a tentação de "já que estou aqui, corrijo" sempre vence — e some a fronteira entre o dado que chegou e o dado que você decidiu.
  3. O que acontece ao rodar duas vezes. Recria a tabela, acrescenta, ou dá erro? Só uma dessas respostas deixa você errar sem medo. Escolha recriar e escreva isso: é o que sustenta a promessa de rodar de novo quando travar.
  4. Como o arquivo é lido. Encoding declarado (utf-8), nunca adivinhado; .csv.gz lido direto, sem descompactar. Duas linhas na spec que economizam a meia hora clássica de caçar acento quebrado.
  5. Quem decide os tipos. Deixar o leitor inferir, ou trazer tudo como texto e converter só na etapa 2? Inferência é confortável até o dia em que ela lê um CEP com zero à esquerda como número e o zero some. Decida — e anote por quê.
  6. O que aparece na tela. Defina o formato da saída: uma linha por tabela, com nome e contagem. Isso não é enfeite, é seu único instrumento de conferência nesta etapa — e é o que você vai comparar com a tabela de contagens.
  7. O que fazer quando der errado. Faltou um arquivo em raw/: para tudo com mensagem clara, ou pula e continua? Prefira parar. Um pipeline que ingere oito de nove tabelas em silêncio produz um dashboard errado que parece certo.

Essa lista é também um bom prompt: entregue as sete decisões escritas para a IA e peça o código. O que você vai avaliar não é se ele roda — é se ele respeita o que você decidiu.

O prompt · spec-driven development

As sete decisões acima, escritas no formato que a IA consegue obedecer. É isso que spec-driven development significa na prática: a spec é o artefato principal, o código é consequência dela. Você revisa a spec antes de rodar, e depois revisa o código contra a spec — não contra a sua intuição.

Estou construindo um pipeline de dados em Python sobre o dataset público da

acrescente requisito que não esteja escrito aqui. Se algo estiver ambíguo,
pergunte antes de escrever código.

STACK

O QUE JÁ EXISTE (use, não reimplemente)
pipeline/db.py expõe:
  PASTA_RAW                          Path da pasta com os nove .csv.gz
  conectar()                         abre o olist.duckdb, criando se faltar
  criar_schema(con, nome)            CREATE SCHEMA IF NOT EXISTS
  gravar(con, df, schema, tabela)    grava e devolve a contagem lida do banco

ARTEFATOS A PRODUZIR
1. pipeline/ingestao.py, executável com:
     uv run python -m pipeline.ingestao
2. ui.py, na raiz do projeto, executável com:
     uv run python ui.py
   (spec própria no fim deste prompt; são dois arquivos que não se importam)

SPEC

1. ESCOPO E NOMES
   Schema de destino: raw
   Mapa arquivo -> tabela, completo e literal:
     olist_orders_dataset.csv.gz               -> pedidos
     olist_order_items_dataset.csv.gz          -> itens_pedido
     olist_order_payments_dataset.csv.gz       -> pagamentos
     olist_order_reviews_dataset.csv.gz        -> avaliacoes
     olist_customers_dataset.csv.gz            -> clientes
     olist_sellers_dataset.csv.gz              -> vendedores
     olist_products_dataset.csv.gz             -> produtos
     product_category_name_translation.csv.gz  -> traducao_categorias
     olist_geolocation_dataset.csv.gz          -> geolocalizacao
   Os nomes vão para o português porque é o vocabulário que vou digitar de
   memória num JOIN nas próximas aulas.

2. PROIBIÇÕES (a regra central desta etapa)
   Nenhuma conversão de tipo. Nenhuma linha descartada ou deduplicada.
   Nenhum nome de coluna alterado. Nenhum valor corrigido, preenchido ou
   normalizado. Data continua texto, nulo continua nulo.
   Motivo: a fronteira entre "o dado que chegou" e "o dado que eu decidi"
   precisa existir em algum lugar, e esse lugar é a passagem de raw para
   refined, na etapa 2. Se a correção acontecer aqui, a fronteira some.

3. REEXECUÇÃO
   Rodar dez vezes tem que dar o mesmo resultado que rodar uma: a tabela é
   recriada (CREATE OR REPLACE), nunca acrescentada. É o que me deixa errar
   sem medo.

4. LEITURA DO ARQUIVO
   encoding declarado como utf-8, nunca adivinhado.
   Os .csv.gz são lidos direto, sem descompactar.
   Campo vazio continua virando nulo; não transforme em string vazia.

5. TIPAGEM
   Toda coluna entra como texto (dtype=str), inferência desligada.
   Motivo: inferência lê CEP com zero à esquerda como número e o zero
   desaparece sem aviso. A conversão acontece na etapa 2, onde é uma
   decisão registrada.

6. SAÍDA NA TELA
   Uma linha por tabela, com nome qualificado e contagem de linhas vinda do
   banco (não do DataFrame), milhar separado por ponto.
   Uma linha final com o total.
   Essa saída é meu único instrumento de conferência nesta etapa.
   O stdout precisa ser reconfigurado para utf-8: rodo no Prompt de Comando
   do Windows, onde acento sai embaralhado por padrão.

7. ERRO
   Antes de abrir o banco, verifique se os nove arquivos existem.
   Faltando qualquer um: liste os que faltam, diga em que pasta procurou e
   encerre com sys.exit(1). Não ingira parcialmente.
   Motivo: ingerir oito de nove tabelas em silêncio produz um dashboard
   errado que parece certo.

CRITÉRIOS DE ACEITE (ingestão)
- A execução imprime nove linhas e um total de 1.550.922 registros.
- Rodar duas vezes seguidas imprime exatamente a mesma coisa.
- SELECT * FROM raw.pedidos devolve todas as colunas como VARCHAR.
- Remover um arquivo da pasta faz o script parar antes de gravar qualquer
  tabela.
- O script termina sozinho e devolve o terminal: nenhum processo fica de pé.

SPEC DO ui.py (segundo artefato)
Quero explorar o banco pelo navegador, em vez de ler tabela no terminal.

U1. O QUE FAZ
    Abre o olist.duckdb da raiz do projeto, instala e carrega a extensão
    `ui` do DuckDB (INSTALL ui; LOAD ui;) e chama CALL start_ui(), que sobe
    o servidor em http://localhost:4213 e abre o navegador.
U2. FICA DE PÉ ATÉ CTRL+C
    A extensão serve enquanto a conexão estiver viva. O script mantém o
    processo rodando, imprime a URL e a instrução "Ctrl+C para encerrar", e
    no Ctrl+C fecha a conexão e sai limpo, sem traceback.
    Motivo: o arquivo .duckdb aceita um único processo escrevendo. Com o
    ui.py de pé, a ingestão falha com "Could not set lock on file". Saber
    exatamente como desligar o servidor faz parte da ferramenta.
U3. NÃO CRIA BANCO
    Se olist.duckdb não existir, diga que é preciso rodar a ingestão antes
    e encerre com sys.exit(1). Por isso NÃO use conectar() de pipeline/db.py,
    que cria o arquivo quando ele falta: um banco vazio aberto no navegador
    parece ingestão quebrada.
U4. SEPARAÇÃO
    ui.py não importa pipeline/ingestao.py, e a ingestão não importa ui.py:
    a ingestão não sobe servidor, não abre navegador e não depende da
    extensão ui para rodar.
U5. SAÍDA NA TELA
    Mesma regra do item 6: stdout reconfigurado para utf-8.

CRITÉRIOS DE ACEITE (ui.py)
- uv run python ui.py abre o navegador em localhost:4213 e o schema raw
  aparece com as nove tabelas.
- Ctrl+C devolve o terminal sem traceback, e logo depois a ingestão roda
  sem erro de lock.
- Renomear olist.duckdb faz o ui.py parar com a mensagem, sem criar arquivo
  novo.

ENTREGA, nesta ordem, para cada um dos dois arquivos
1. A spec como docstring no topo do arquivo, dizendo por que cada regra
   existe — não só o que ela manda fazer.
2. O código, com comentários apenas onde a decisão não é óbvia pelo código.
3. Uma lista final do que você assumiu e que não estava na spec. Se a lista
   não estiver vazia, é a minha spec que precisa melhorar.

Repare no item 3 da entrega. Ele é o truque do método: tudo que a IA precisou assumir é um buraco na sua spec, e vira a próxima linha dela. Dois ciclos disso e a spec passa a valer mais que o código — porque é dela que sai o código de novo, quando a etapa 2 mudar de ideia sobre alguma coisa.

03

Rodar a ingestão

CSV → schema raw no olist.duckdb

A regra desta etapa é a mais fácil de dizer e a mais fácil de trair: não transforme nada. Data continua texto, nulo continua nulo, nome de coluna continua o que veio. A tentação de "já que estou aqui, deixa eu corrigir" é exatamente o que faz pipeline virar caixa-preta.

uv run python -m pipeline.ingestao

Cada tabela ingerida se anuncia:

✓ raw.pedidos              99.441 linhas
✓ raw.itens_pedido        112.650 linhas
✓ raw.clientes             99.441 linhas

Confira

Os números da tela batem com a tabela de contagens? Então a ingestão está certa. Não bateu — não continue. Dado errado aqui contamina tudo que vem depois, e você vai caçar o erro três etapas adiante.

04

Olhar o dado com os próprios olhos

O primeiro SELECT, no notebook do DuckDB

O DuckDB tem interface web própria, e ela roda na sua máquina. Suba o servidor:

uv run python ui.py

O navegador abre em localhost:4213. À esquerda, os schemas do banco — clique em raw e as nove tabelas estão lá, com as colunas de cada uma. Clicar numa tabela já mostra as primeiras linhas, sem escrever nada.

À direita fica o notebook: células de SQL, uma embaixo da outra, cada uma com seu resultado em tabela logo abaixo. É o mesmo formato de um notebook de Python — só que a linguagem é SQL e o resultado sai direto do banco. Rode cada célula com Ctrl+Enter.

Célula 1 · as primeiras linhas

SELECT * FROM raw.pedidos LIMIT 5;

Célula 2 · que colunas existem, e de que tipo

DESCRIBE raw.pedidos;

Célula 3 · o tamanho da coisa

SELECT count(*) AS linhas FROM raw.pedidos;

Guarde o notebook aberto: ele volta em todas as aulas. A partir daqui, toda pergunta que você tiver sobre o dado se responde numa célula nova — e é assim que os SELECT da etapa 3 vão nascer, testados um por um antes de virarem arquivo .sql.

Encerre o servidor antes de rodar o pipeline. O arquivo olist.duckdb aceita um único processo escrevendo nele. Com o ui.py de pé, a transformação da próxima aula falha com IO Error: Could not set lock on file — que parece corrupção de banco e não é. Ctrl+C no terminal do ui.py resolve. A regra do curso: servidor para olhar, terminal para escrever, nunca os dois ao mesmo tempo.
Na primeira vez o DuckDB baixa a extensão ui. São poucos megabytes e precisa de internet, uma vez só. Depois disso funciona offline.

Confira

Na célula 2, repare no tipo das colunas de data: VARCHAR, texto puro — e order_id também. Guarde essa imagem, porque é exatamente o que a etapa 2 vai consertar: rodar o mesmo DESCRIBE em refined.pedidos e ver TIMESTAMP no lugar é como você vai saber que ela funcionou.

A extensão não baixou — como olhar o dado pelo terminal

Rede corporativa costuma bloquear o download da extensão. O plano B devolve as mesmas cinco linhas, só mais feio:

uv run python -X utf8 -c "import duckdb; print(duckdb.connect('olist.duckdb').sql('SELECT * FROM raw.pedidos LIMIT 5'))"

O -X utf8 não é decoração: o DuckDB desenha a tabela com caracteres de moldura, e o Prompt de Comando do Windows, que por padrão não fala UTF-8, estoura com UnicodeEncodeError: 'charmap' codec can't encode characters. Parece erro de código e não é — o dado está perfeito, quem não sabe imprimir é o terminal.

As etapas 2 a 5 abrem depois da aula 1. O caminho inteiro está desenhado na arquitetura e resumido em os quatro encontros — o passo a passo de cada etapa é liberado no fim do encontro anterior, para a turma chegar na aula sem ter lido a resposta.

Etapa 2 — Transformação

Aula 2 · pipeline/transformacao.py

05

De raw para refined

Onde o dado passa a merecer confiança

Três coisas acontecem aqui, e a terceira é a que separa quem sabe de quem copia:

  1. Tipo. Texto que é data vira TIMESTAMP, com formato declarado — nunca adivinhado.
  2. Duplicata. Some, mas só depois de você saber quantas eram e por que existiam.
  3. Nulo. Cada um vira uma decisão explícita e escrita. Um pedido sem data_aprovacao não é um erro no arquivo: é um pedido que nunca foi aprovado. Isso é informação. Apagar a linha seria apagar um fato.
uv run python -m pipeline.transformacao

A saída mostra o antes e o depois, que é a parte que ensina:

refined.pedidos    99.441 → 99.441 linhas   (0 duplicatas)
  data_aprovacao: nulos mantidos (pedido não aprovado — é informação, não erro)

Confira

Toda linha que sumiu tem que ter explicação. Se entraram 99.441 e saíram 98.900, você precisa saber o nome das 541 — e concordar com o sumiço. "Deve ser lixo" não é resposta.

06 · Método

A IA é copiloto — e copiloto se confere

Use Claude, ChatGPT, o que preferir, à vontade, o curso inteiro. Não tem nada de errado em pedir a função pronta. O que tem de errado é colar sem conferir — e essa é a habilidade que o curso realmente treina.

O motivo é específico: em código de dados, o erro da IA quase nunca estoura. Ela escreve um JOIN que roda liso e duplica 4.000 linhas. Um dropna() que apaga 12% da base em silêncio. Um parse de data que lê 03/04 como 4 de março. Nada disso lança exceção. O código "funciona" e o número está errado — que é o pior defeito possível, porque alguém vai decidir com base nele.

Daí o hábito, que vale para cada sugestão que você aceitar:

  1. Conte antes. Quantas linhas tem agora?
  2. Rode.
  3. Conte depois. Mudou? Você sabia que ia mudar? Consegue explicar a diferença exata?

São três segundos. É por isso que cada etapa deste pipeline imprime contagem na tela — o hábito está embutido na ferramenta, para você não precisar lembrar dele.

07 · Para casa

O desafio da aula 1

Um desafio por aula, entregue no fim do encontro e corrigido ao vivo no começo do seguinte. Todos seguem a mesma regra: usam o que foi dado em aula, mas exigem um passo que não foi mostrado. É de propósito — é o degrau que separa consolidar de copiar.

Traga feito. Se não saiu, traga quebrado: erro de todo mundo na tela é a parte mais útil da correção, e quem só assiste acerto nunca aprende a depurar.

01ingestão

O que esse dado é capaz de responder

Abra o notebook do DuckDB e passeie pelas nove tabelas de raw: coluna por coluna, uma por uma. Depois escreva dez indicadores que esse dado permitiria calcular — e, para cada um, de que tabelas ele sai.

Nada de SQL ainda: o desafio é de leitura, não de código. Uma linha por indicador, neste formato:

Ticket médio por pedido — itens_pedido (preco) + pedidos (order_id) — mede quanto vale uma venda típica

Três regras para a lista não virar chute:

  1. Só vale o que o dado sustenta. Se nenhuma coluna te dá a informação, o indicador não entra — por mais que o negócio quisesse. Descobrir isso é metade do exercício: margem de lucro, por exemplo, não tem como sair daqui, e saber dizer por quê vale mais que dez indicadores fáceis.
  2. Diga de onde sai. Nome da tabela e da coluna. É aqui que você descobre que quase nada interessante mora numa tabela só — e é esse o motivo de existir JOIN.
  3. Pelo menos três precisam cruzar duas tabelas ou mais. Os indicadores de uma tabela só são os óbvios; os bons atravessam.

Marque com um ? os que você não tem certeza se dão. Esses são os melhores — e são o começo da aula 2.

Entrega: a lista dos dez, em indicadores.md na raiz do projeto, colada no formulário de entrega do desafio 1 (precisa de conta no GitHub). Vamos ler em voz alta na correção e escolher juntos quais viram os marts do curso.

02transformação

Limpar o que não tem resposta certa

A tabela de avaliações tem texto livre, nulo em quantidade e datas fora de ordem. Limpe — e justifique cada escolha por escrito. Sem justificativa não vale, porque o que está sendo avaliado é o critério, não o código.

Entrega: a tabela em refined e uma linha de justificativa por decisão tomada.

03SQL

O quinto mart

Escreva 05_ticket_medio_por_estado.sql: o ticket médio por estado do cliente. Ele precisa de um JOIN que não apareceu em aula — o estado está em clientes, o valor está em itens_pedido, e os dois não se tocam diretamente. Descobrir o caminho entre eles é o desafio.

Entrega: o arquivo .sql rodando e a tabela em marts, não vazia.

04dash

Fechar o ciclo

Coloque o seu quinto mart no dashboard, com um filtro novo, e escreva um teste que garanta que ele nunca volta vazio. É o curso inteiro em miniatura: uma pergunta de negócio que atravessa SQL, apresentação e verificação.

Entrega: o gráfico no app.py e o teste passando em uv run pytest.

A2 · Anexo

Quando quebrar

Acentos viraram símbolos estranhos

O CSV é UTF-8 e o Python assumiu outro encoding. Declare sempre: encoding="utf-8". Nunca deixe adivinhar — no Windows o palpite costuma ser cp1252, e aí São Paulo vira SÃ£o Paulo.

As datas estão certas, mas o mês é o dia

Clássico brasileiro: 03/04/2017 lido como 4 de março. Declare o formato ao converter em vez de aceitar inferência. O sintoma que entrega o problema é um gráfico mensal em que só existem dados até o dia 12.

A geolocalização demora uma eternidade

Ela tem 1.000.163 linhas — sozinha, é dois terços do dataset inteiro. Não está travada, está trabalhando. É exatamente por isso que ela fica fora da aula 1 e vira desafio.

Um mart voltou vazio

Quase sempre é um JOIN que não casou. Rode um COUNT em cada lado separado antes de juntar: se os dois têm linhas e o JOIN não tem, o problema é a chave — tipo diferente, espaço sobrando, ou maiúscula contra minúscula.

Quebrei tudo e não sei onde

Esta é a saída de emergência, e usar não é vergonha nenhuma:

uv run python executar.py

Apaga o banco, roda ingestão, transformação e marts na ordem, e te devolve exatamente onde a turma está. Existe para isto.
